# Design decisions

Resolved 2026-09-06 in review of the implementation plan, before any Phase 0 work. These are binding on implementing agents. Each maps to the milestone that must honor it. Changing one requires an ADR.

| # | Decision | Lands in |
|---|---|---|
| D1 | **Task lifecycle.** A tool returning a `Task` handle appends a "task started" tool result and the model may keep working. Tasks live in `State.pending_tasks` with states `pending`, `running`, `succeeded`, `failed`, `cancelled`. Completion arrives as a `TaskUpdate` event from a waker; the kernel appends a synthetic tool result carrying the outcome, resuming the session if suspended or injecting at the next turn boundary. Suspension rule: a turn ends with no tool calls and pending tasks exist. `check_hint` is for the polling sidecar and is never shown to the model. P1 ships an in-kernel process-exit waker for a `run_script` tool. | P1.0, P1.1, P1.2, P1.7 |
| D2 | **Session states.** `created`, `running`, `idle` (waiting for user), `suspended` (waiting for a waker), `done` (explicit end only), `failed` (last checkpoint kept, resumable). A user message in `idle` or `suspended` moves to `running`; a message while `running` is queued until the turn boundary. | P1.0, P1.2 |
| D3 | **Hashing.** BLAKE3 over RFC 8785 canonical JSON. Every log line is an envelope `{seq, ts, session_id, kind, payload}`; hashes cover the payload only. Hash strings carry an algorithm prefix (`b3:<hex>`). The state hash covers `State` minus an enumerated list of volatile fields. | P1.0, P1.1, P1.3 |
| D4 | **Runtime and process model.** tokio; async traits for `Tool`, `Provider`, `Middleware`. One kernel process serves one session over stdio. The P1.9 daemon is a supervisor that spawns a kernel process per session and proxies the unix socket to it; it is the seed of the P3 orchestrator. | P1.2, P1.9, P3.3 |
| D5 | **Sandbox shape.** `Tool` has a `kind`: `Stateless` (fresh bwrap per call; bash state does not persist) or `Session` (one bwrap process per session under the derived policy; calls are RPC into it; Python REPL, MCP servers). First-party compiled tools (`read`, `write`, `edit`) enforce the same policy via path checks in the Host layer, in process. Everything from the mutable layer (bash commands, Python code, agent-authored extensions) runs out of process under bwrap. | P1.6, P1.7 |
| D6 | **Capability algebra.** Capabilities are typed atoms: `Fs{path, mode}`, `Net{allowlist}`, `Proc{spawn}`, `Tool{name}`, `Spawn{catalog_name}`, `Secret{name}`. Narrower-than is defined per atom (path prefix, `ro` below `rw`, allowlist subset, exact name). Domain bundles (`meshing`, `solver`, `post`) are named atom sets in a bundles file in `profiles`, expanded at resolution time; the kernel and sandbox see only atoms. HPC in-house tools are granted as `Fs{<install path>, ro}` plus `Proc{sbatch}`. | P1.0, P1.1, P1.7, P1.8, P2.4 |
| D7 | **Profiles.** TOML. Scalars override, tables deep-merge, lists replace. Middleware chain: model and agent profiles contribute named entries with a priority; resolved chain is a stable sort; the model profile's tool-call parser has a fixed early slot. Validator rejects unknown keys, kernel-only keys, and capabilities exceeding grants. System prompt is assembled as separate blocks in fixed order: model prompt variant, agent role prompt, `AGENTS.md`, active skills, notebook (on resume). | P1.0, P1.8 |
| D8 | **Extension tiers.** Middleware and first-party tools are compiled Rust behind the `ext` API. Agent-authorable extensions are out-of-process tools only; the P0.3 spike chooses between process JSON-RPC and WASM for those. The agent can author tools, skills, workflows, and profiles at runtime, not middleware. | P0.3, P2.1 |
| D9 | **Simulation toolchain.** In-house tools, pre-installed at fixed paths on HPC, invoked via Slurm. They are placeholders in this plan; sub-agents and tooling around them come later. CI uses a mock solver that behaves like a Slurm-submitted job and emits a plausible log. | P0.5, P2.8, P3.6, P4.2 |
| D10 | **Secrets.** Host returns secret handles; only provider clients resolve them at request time. The log writer redacts every payload against known secret values and common token patterns before writing. Tool sandboxes get a scrubbed environment and never inherit API keys. | P1.3, P1.6, P1.7 |
| D11 | **Transport and auth.** Unix socket with file permissions plus peer-credential check. Remote access is an SSH-forwarded unix socket to the HPC login node. Websocket auth and OpenShift access patterns are backlogged pending the security team. | P1.9, Backlog |
| D12 | **Kernel freeze.** Soft freeze at P1 exit (ADR required, expected); hard freeze at P2 exit. `ArtifactStore` and `Memory` traits are defined in `kernel` in P1 with no-op implementations. Result spill lives in the kernel, using `ArtifactStore`, so a profile cannot disable it. | P1.1, P1.2, P1 exit, P2 exit |
| D13 | **Provenance-ready events.** From P1.1: tool call events carry the argument hash; tool result events carry the result hash and artifact handles; model call events carry request hash, response hash, token usage, model id, and active profile hashes. | P1.1 |
| D14 | **Platforms.** The kernel is deployed only on Linux. Clients run on Windows, macOS, and Linux. macOS local development is a convenience: kernel inside a Podman machine with the real bwrap stack, or a `None` sandbox backend that is compiled only in development builds and logged in every run. Windows developers use WSL2. The sandbox backend is an explicit trait. | P1.7 |
| D15 | **Kernel behaviors.** Cancellation: a protocol message sets a token, the loop checks it between hooks, the sandbox launcher sends SIGTERM to a running tool, and the cancellation is logged. Provider errors: retry with backoff on rate limits and server errors up to a fixed count, then the turn fails and the session enters `failed` with its checkpoint intact. Crash recovery: on start with an existing log, restore the last checkpoint and discard events after it. Images: `ContentBlock::Image{artifact_handle, mime}`; the provider encodes bytes at request time. | P1.1, P1.2, P1.5, P1.9 |
| D16 | **Definitions.** Deterministic replay: replayed event payloads, after stripping envelope fields, are byte-identical to the recorded ones, asserted by a `diff-logs` command. Context budget: placeholder 40k tokens per turn in the agent profile, to be tuned. The P4 "correctly rejected" case is constructed deliberately with an overfit prompt. | P1.4, P2.9, P4 exit |
| D17 | **`ask_user`.** The Host's UI prompt capability is a tool for asking the user a question; the answer is logged as a user message. Permission is never asked; sandbox policy already answered it. | P1.6, P1.9 |
| D18 | **Deployment target and CI stand-in.** The kernel runs in rootless Podman on the HPC login node using the site's uidmap flags (`podman run --uidmap 0:0:2000 --uidmap 65534:2000:2`; build with `--userns-uid-map=0:0:1 --userns-uid-map=1:1:1999 --userns-uid-map=65534:2000:2`). P0.1 tests Podman → outer bwrap → inner bwrap under exactly that map, with bwrap directly on the login node as the fallback. CI runs a CPU stack: llama.cpp server as the OpenAI-compatible endpoint with a small tool-calling model, a real LiteLLM proxy routing to it, a fake `sbatch` that runs the job in the background and calls the epilog hook, and the D9 mock solver. vLLM-specific behavior is behind an environment gate for human-run tests. | P0.1, P0.5, P3.3 |
| D19 | **Hidden eval set.** A separate private repository, mounted only into the eval runner's sandbox. The proposer's sandbox policy never mounts it and a test asserts that. The hidden half is owned by a named person. | P4.2 |
| D20 | **P1.0 specs.** Three human-reviewed specs precede P1.1: kernel interface as Rust signatures including the D1 and D2 state machines; event and hash schema (D3, D13); profile and capability schema (D6, D7). | P1.0 |
